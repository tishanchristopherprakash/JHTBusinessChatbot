Overall it's a decent foundation for a local RAG app, but there are a few areas worth looking at:

What's done well:

@st.cache_resource is the right call for the vector store — avoids re-indexing on every rerun
temperature: 0.0 is a smart choice for a factual business assistant
utf-8-sig with errors='ignore' handles messy Word-exported text gracefully
Streaming response with the cursor effect is a nice UX touch
Concerns worth addressing:

Retrieval quality — k=2 is quite low. If the answer spans multiple chunks, you might miss context. Also chunk_overlap=30 is very small relative to chunk_size=1000, so you risk cutting sentences mid-thought at boundaries.

Single file limitation — It's hardcoded to one info.txt. If your knowledge base grows, this becomes a bottleneck with no easy way to add sources.

No retrieval feedback — The user has no idea why the bot answered a certain way or if the context was actually relevant. Adding source chunk display (even collapsible) helps with trust and debugging.

Conversation history risk — You're passing the last 4 messages back to the LLM, but the system prompt is rebuilt fresh each turn with new context. If the user's follow-up question is vague (e.g. "tell me more"), the similarity search runs against that vague query, not the original topic, so retrieval can go off-track.

No fallback if vector_db is None — If info.txt is missing, the bot still runs but answers purely from the LLM with no grounding, which contradicts the "ONLY the context facts" instruction in the system prompt.

The biggest architectural gap is probably the vague follow-up query problem — it's a very common RAG failure mode. Would you like suggestions on how to address any of these specifically?
